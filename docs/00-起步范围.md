# 起步范围

状态：2026-11-13 更新为 Skill 1.0 的落地范围：两种建模入口、按需查询、设计迭代和通用离线画布。用户选定 BenchGo 总架构页的空间画布方向，当前支持单层模块钻取与父级恢复。其他文档中关于“首版”“v0.1”的范围描述与本文件不一致时，以本文件为准；那些文档保留为待验证的设计建议，不代表当前要做。

## 当前验证目标

用户明确了两种核心情况：还没有系统、只有想法；已有系统，希望深入理解以便以后迭代。因此先用两条路线验证同一个闭环：输入 → 建模 → 校验 → 画布阅读 → 提出下一轮修改。已有系统路线由用户选择 ArkiGo 自身，新系统路线使用明确标注的任务清单演示需求。

[POC 入口与验证记录](./poc/README.md)提供[四级用户注册](./poc/canvas-engine/registration.html)、引擎架构、任务清单及原始模型的离线画布。已有校验工具继续使用；当前已补齐 query 有界上下文读取、diff 程序差异和 apply 候选应用。完整证据机制、自动业务影响推断仍后置。验收见 [Skill 记录](./07-Skill验收.md)。

## 为什么缩减

缩减范围时只有文档和样例，没有可运行的东西。原定首版同时包含模型工具、Skill、语义缩放画布、实现证据和可靠更新机制，其中成本最高的几项都依赖两个尚未验证的前提：

1. 模型能否表达一次真实的设计变化，并由程序准确说出改了什么。
2. 用户和 AI 是否愿意、也能够在多轮迭代中持续维护这份模型。

起步版只做验证这两点所需的最小部分，其余内容等有了实际使用结果再决定。

## 起步版包含什么

| 部分 | 内容 |
| --- | --- |
| 模型 | [03](./03-设计模型与文件协议.md) 中的七种对象、五种关系、`parentId` 归属、`designStatus` 和 `provenance`，不新增类型 |
| 工作区 | 新项目默认 `docs/`：`model.json` 或按需使用的 `canvas.json`、生成的 `canvas.html`；有提案时在 `proposals/<change-id>/` 保留 `base.json`、`candidate.json`、`request.md`。用户指定位置优先，已有设计沿用原位置 |
| `validate` | 结构检查和流程检查，返回对象 ID 与字段路径；另外只提示两类缺口：规则没有验收关联、问题仍未决 |
| `diff` | 已实现：按稳定 ID 比较，区分内容、布局、revision；有界输出与分页 |
| `query` | 已实现有界上下文查询：索引、名称/来源检索、视图/节点/字段读取、一跳关联、分页与省略标记 |
| `apply` | 校验候选并生成 HTML，检查基线冲突后应用；普通写入失败尝试恢复，保留基线/候选 |
| Skill | 从想法设计、从代码理解；已有设计通过查询与基线/候选流程迭代，支持独立安装 |
| 画布 | 自包含离线 HTML：分区、节点、避障折线、模块进入/返回与面包屑、平移缩放、详情、当前视图搜索和主题切换；分区内拖动、浏览器保存、布局导出与导入；不需要服务或构建 |
| 画布输入 | `arkigo-canvas/1` 描述编排；可选 `rootViewId` 与节点 `targetViewId` 构成经校验的单根树，兼容原设计模型的默认投影。AI 提供分析与内容，引擎提供公共显示和交互，不自动扫描仓库 |

候选应用由 `apply.mjs` 完成：先校验并渲染，确认当前输入与 base 一致，且候选更新 revision，再写入 JSON 与 HTML。文档 ID/协议保持一致；冲突拒绝覆盖。提案目录保留为设计历史，不承诺断电恢复或多进程事务。

工具是放在 `skills/arkigo/scripts/` 下、无构建步骤的 Node 脚本。JSON Schema 负责字段和类型，引用、归属无环、流程可达等 Schema 表达不了的检查由脚本完成。

用户进一步明确的约束是“轻量又高效”：不引入常驻服务、数据库或构建流程；Skill 主文件保持短小，按任务读取参考资料；每轮只设计当前必要范围。校验使用一个直接依赖 Ajv，避免重复实现 JSON Schema 标准；日常使用只返回结果与必要诊断。减少上下文的 query 工具已加入：默认 20 项、12,000 UTF-8 字节，按需分页或细分字段；不限制其他工具输出，也不是 token 预算。

早期 POC 由当前会话执行；Skill 1.0 的独立任务验收见 Skill 记录。宿主自动发现与实际使用效果需在用户会话中继续观察，文件生成不等于产品效果证明。

体验时回答：

- 从想法生成的设计是否表达了用户想做的东西，建议与未知项是否清楚。
- 对已有系统的理解是否准确，关键行为能否追溯到代码位置。
- 画布是否让阅读与提出修改更方便；生成及维护是否值得。

## 试用之后再决定

- 当前模块放大进入、缩小返回与父级位置恢复是否便于理解；是否值得进一步做全层同时 LOD 和关系聚合。
- 是否需要从模型生成 Markdown 大纲作为过渡的阅读方式。
- AI 继续直接编辑整份候选文件，还是改为按对象的补丁式命令。
- 实现证据与代码核对的优先级。
