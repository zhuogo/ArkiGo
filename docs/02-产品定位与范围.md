# 产品定位与范围

## 产品定义

ArkiGo 是一个面向 AI 辅助开发的系统设计 Skill 与本地设计工作区。它把想法整理成具有明确对象、关系、规则和验收依据的设计模型，以语义缩放画布呈现，并在开发和迭代时维护设计与实现的关联。

它可以成为传统 PRD 的主要替代载体。自然语言仍然用于表达目标、理由与规则；图、原型和结构化数据用于表达文字不容易展示的关系和行为。

## 主要用户与任务

首要用户是反复使用 AI 开发 Web 系统的个人开发者和小团队。起点既可能是一个想法，也可能是已有项目。

| 用户任务 | 用户应得到的结果 |
| --- | --- |
| “我有一个产品想法” | 系统范围、核心模块、主流程、异常及待决策问题的草案 |
| “我想看懂之前做的系统” | 有代码依据的现状地图，明确未知内容，补充设计意图的位置 |
| “我要增加一个能力” | 可审阅的设计变化、直接修改对象、可能受影响对象及原因 |
| “让 AI 开始实现” | 与目标模块有关的规则、接口、验收及代码线索 |
| “做完了，检查设计是否还一致” | 对应实现与验证记录，未完成项及证据失效提示 |

## 主要体验

用户先看到整个系统的模块布局及变化分布；放大一个模块，逐步看到子模块、流程、规则与验收；选中某个对象，再查看其来源、待定问题、关联代码或版本差异。

同一条规则不需要在几张图里重复维护。多个视图引用同一个规则对象，修改后各视图呈现同一份新内容。

新增需求的第一份输出是设计草案。用户已经明确决定的内容直接记录；AI 补充的建议显式标记，只有影响下一步工作的未知决策需要澄清，不把每次修改都变成审批流程。

## 必须解决的正确性问题

- 图上出现模块，不代表业务逻辑已完整。
- 文件路径存在，不代表目标功能已实现。
- 测试通过，只说明对应版本下的特定场景有证据。
- 关系可达，只说明存在已记录的关联，不代表真实运行时必然受影响。
- 前置设计允许被原型和反馈修正，不要求一次写完系统所有细节。

这些区别要体现在模型和展示中，不能仅靠文档提醒。

## v0.1 的完整范围

> 2026-11-12：当前只做其中的一部分，见[起步范围](./00-起步范围.md)。本节和下面的验收场景描述的是完整目标，其中画布、媒体、布局差异和代码证据已推迟。

首版以“对话编辑、本地查看”为主，让一次设计迭代真正跑通。

| 能力 | 首版要求 |
| --- | --- |
| 输入 | 支持产品描述；支持读取一个已有项目的相关代码片段 |
| 设计 | 系统、模块、流程、步骤、规则、验收、问题的稳定对象 |
| 关系 | 层级归属、步骤流转、依赖、规则约束和验收覆盖 |
| 画布 | 至少三种语义展示密度、嵌套容器、跨模块关系、搜索与面包屑 |
| 媒体 | Markdown 文本、图片附件、原型链接；音视频先作为有标题的附件链接 |
| 变更 | 比较基线和候选设计，分开显示内容、关系和布局变化 |
| 代码 | 记录规划位置与实际证据，检查实际文件及版本是否匹配 |
| 输出 | 可编辑的设计文件、本地画布页面、按模块提取的 AI 上下文 |
| 编辑 | AI 通过 Skill 和模型工具修改；画布先提供浏览和比较 |

首版不覆盖多人实时协作、账号与云同步、完整白板编辑器、自动重构代码、所有图种、所有语言的静态分析、无限层级的性能承诺。MCP 在确有跨客户端接入需求时再做。

## 首版验收场景

以一个示例 Web 应用的登录模块为主线：初版有凭证检查，第二版增加失败次数限制及恢复规则。样例中的规则是演示假设，不是推荐的生产安全方案。

1. 输入简单需求后，画布能显示用户系统、登录流程、规则和待定问题。
2. 缩远只看模块；放大看到步骤；再深入显示规则与验收，过程中保持同一对象身份和位置上下文。
3. 提出增加限流后，保留原登录模块 ID，显示新增步骤、规则及验收，显示两项未决问题。
4. 只移动卡片时，不出现“业务逻辑修改”的计数。
5. 对已有规则改写后，之前的验证证据不再直接代表新规则已验证。
6. 读取代码时，无法找到依据的行为标为未知；没有代码的前置设计也能正常生成。
7. 新一轮 AI 会话只读取目标模块及相关规则、验收和依赖，就能指出该修改涉及的范围；不会因只看到局部而把遗漏对象当作不存在。
