# 登录模块：一轮设计变更样例

本目录是协议讨论用的演示数据，所有需求、接受状态、规则和验收均为假设，不代表用户已确认的真实业务规则，也不是生产登录安全方案。代码定位仅是规划位置，未指向本项目中已存在的登录实现。

## 文件

| 文件 | 内容 |
| --- | --- |
| [login.base.json](./login.base.json) | 假设已经接受的初始登录设计 |
| [login.candidate.json](./login.candidate.json) | 增加失败次数限制的候选设计，改动保持待定状态 |
| [login.view.json](./login.view.json) | 独立于业务内容的模块相对位置与视图偏好 |
| [login.implementation-plan.json](./login.implementation-plan.json) | 规划中的代码位置，没有伪造实现或通过证据 |

[起步范围](../00-起步范围.md)的工具只读取 `login.base.json` 和 `login.candidate.json`；视图和实现规划两份文件保留作后续参考。

这里没有生成 `delta.json`：真实差异应由未来工具根据两个输入计算，不能把手写说明伪装成程序计算结果。

## 本轮需求

“连续输错密码后暂时限制继续尝试，并允许在限制时间结束后重新验证。”

候选规则暂定为连续五次失败锁定十分钟，成功和锁定期满时清零。计数主体及多实例共享方案仍是待决策问题，因此相关实现尚未准备完成。

样例刻意保持较小规模：验证依赖故障和计数存储不可用虽已写入流程与规则，尚未分别建立完整验收场景。起步版只检查规则是否有关联验收，不能自动识别这些分支缺口，也不能因规则存在两条验收关联就宣布所有分支已覆盖。

两份模型已通过 [validate](../../skills/arkigo/README.md)；基线为 0 个错误、0 个提示，候选为 0 个错误、2 个未决问题提示。失败场景见[校验测试样例](../../skills/arkigo/tests/fixtures/README.md)。

预期设计差异：

- 保留系统、用户模块、登录流程及原有步骤的 ID。
- 新增限流检查步骤、规则、两项验收和两项问题。
- 将“接收请求 → 凭证检查”改为“接收请求 → 限流检查 → 凭证检查”。
- 限流检查增加“限制有效 → 返回失败”的分支。
- 凭证检查记录失败计数和清零动作，规则详情提供依据。
- 初始成功与失败验收补充“当前不受限制”的前置条件。
- 无证据文件，因此不能显示“功能已实现”或“测试已通过”。

## 在画布中的预期表现

概览只显示示例应用与用户模块；进入用户模块看到登录流程；深入流程看到步骤、条件、规则与验收。问题显示独立标记，点击可看受影响对象。

比较候选与基线时显示新增和改写对象；被改变端点的关系按关系变化展示。将限流步骤左右移动只应修改 `login.view.json`，不能制造规则差异。

本目录所有“预期”都是未来实现的验收依据。当前只有数据文件，没有可运行的语义缩放页面。
