# ArkiGo

ArkiGo 让一个项目只有一份设计。目标与范围、角色、模块、流程、规则、数据、接口、界面、验收、还没定的问题，以及每一项做到哪了，都写在 `docs/arkigo/design.json` 里。这份内容有两种读者：人打开生成的 `index.html` 浏览路线图和对象详情；AI 用命令按需读取，开工前取材料，写完代码回写。项目里不再另写需求文档和设计文档。

只留一份，是因为两份一定会对不上，而对不上的设计比没有设计更糟：人按它做决定，AI 按它写代码，错都错在看不见的地方。所以你在这里的工作不是画一张图交差，而是让这份设计一直是真的：写进去的每一句有出处，没定的事标成没定，代码变了设计跟着变。

## 分工

- **你写内容和关系，程序做其余的事。** 校验、排版、生成页面、记录每次变更、核对代码依据，都由 `scripts/arkigo.mjs` 完成。你不写坐标和 HTML，也不直接编辑 `design.json`：绕过命令的修改没有校验，没有变更记录，页面不会更新。
- **人拍板，你执行。** 用户说过的要求和做过的决定是设计里最硬的部分。你可以提议，但提议要让用户一眼看出是提议；还没定的问题写成待定项交给用户，不替用户选。
- **程序不替你下结论。** 它只检查结构，并指出依据文件有没有变化；它不扫描仓库，不判断业务是否完整。读代码、理解业务、判断一段代码是否真的做到了某条规则，是你的工作。

## 运行

`<skill-dir>` 是本文件所在的目录。所有操作只有一个入口，下文简写为 `arkigo`：

```sh
node "<skill-dir>/scripts/arkigo.mjs" <命令> [参数]
```

- 需要 Node.js 22 及以上。第一次使用先运行 `arkigo version`：输出里 `dependencies.ajv` 为 `false` 时，在 `<skill-dir>` 里执行一次 `npm ci --omit=dev --ignore-scripts --no-audit --no-fund`。之后不需要网络、服务或构建。
- 在用户项目里的任何目录运行都可以：命令从当前目录向上找最近的 `docs/arkigo/design.json`，也可以用 `--dir <目录>` 指定。
- 输出是单行 JSON，`context` 和 `export md` 输出 Markdown，错误写到标准错误。
- 退出码：0 成功；1 内容问题（校验没过、`verify` 发现依据需要复查、`check --strict` 有提示）；2 用法或读写错误；3 设计在你读过之后被改动过。退出码 1 多数时候是在告诉你设计里有什么情况，不是工具坏了，先读它的输出。

## 读：按需取，不整份读

设计可能有几百个对象。不要直接读 `design.json` 或 `index.html`，用命令取这次需要的部分：

```sh
arkigo query                          # 项目概况：各类型数量、两层目录、未决问题数量、当前 rev
arkigo query --search "退款"           # 全文搜索，结果带对象 id 和命中位置
arkigo query --id order.refund        # 一个对象的完整内容、它的关系、直接下级
arkigo query --type rule --under order --status proposed
arkigo context order.refund           # 写这部分代码前的开工材料
```

读取类命令一次最多返回 20 项、12,000 字节。输出里 `nextOffset` 不为 `null` 或 `omitted` 为 `true` 时，后面还有内容：用 `--offset` 接着取，或者缩小范围。没有返回的内容不等于不存在。

## 写：一次 `change` 是一件说得清的事

所有修改都通过 `change`。一组修改项要么全部写入，要么一项都不写；写入后程序自动重新生成页面，并留下一条变更记录。

```sh
arkigo change --reason "按用户要求增加退款审核" --by codex --ops ops.json
```

- `--reason` 会写入命令历史。写成用户读得懂的一句话，说明做了什么、为什么；不要写「更新设计」这种看不出内容的话。`--by` 写你是谁。
- 一件事放进一次 `change`，不相干的事分开写。第一次建立设计时按模块分批，每批一条说得清的原因。
- 校验没过时什么都不会写入，错误里有对象 `id` 和字段路径，改好再来。没把握时先加 `--dry-run`。
- 从你读设计到写入之间如果隔了较久，或者可能有别人同时在改，带上 `--base <你读到的 rev>`。退出码 3 表示设计已经变了：重新读，再决定怎么改。

修改项和对象的写法见 [格式](references/format.md)。

## 写进去的每一项，分清三件事

这三件事互相独立，页面分开显示。不要从一件推出另一件。

**谁的决定：`origin` 和 `status`。** `origin` 记内容从哪来，`status` 记用户是否已经认可。

| 内容 | `origin` | `status` |
| --- | --- | --- |
| 用户说的要求、做的决定 | `user` | `accepted` |
| 现有文档里写明的 | `doc`，带 `sources` | `accepted` |
| 你从代码里读到的现有行为 | `code`，带 `sources` | `accepted` |
| 你提出的新内容、对意图的推测、改进建议 | `ai` | `proposed` |

只把真正需要用户在对话里确认的内容标成 `proposed`。已经在运行的代码和已经写明的文档是既成事实，如实记录即可；你对它们的理解没有把握时，不要用 `proposed` 表达没把握，而是在 `notes` 里写明哪里没核实，或把疑问写成待定项。

**代码做到哪了：`implementation`。** 取值 `planned`、`partial`、`implemented`，没有这个字段表示没核对过。写 `implemented` 的前提是你读过代码，确认它做到了这个对象描述的事，并给出代码位置；找到一个同名文件不算。它不代表测试通过，也不代表已经上线。

**验收跑过没有：`verification`。** 只有实际执行过的验证才写 `passed` 或 `failed`。读过测试代码不算跑过。

## 没定的事交给用户

遇到会改变做法而用户没说过的事（两种都合理的做法、文档和代码矛盾、业务规则不明确），建一个 `decision`：`question` 写成用户能直接回答的问题，`options` 列出可选的做法，各自的后果写在 `detail` 里，再用 `blocks` 关系指向被它卡住的对象。在对话里请用户决定。不知道就写不知道，不要用常见做法把空白补成事实。

已接受的内容是用户的决定。你认为它该改时不要直接改掉：同样建一个待定项，选项里包含「保持现状」，等用户选了再改。用户明确要求的修改直接改。`decide` 只用来记录用户已经做出的选择。

## 做完之后告诉用户

- 页面在哪：`docs/arkigo/index.html`，双击就能打开，不需要联网。
- 这次改了什么，哪些是你的提议。
- 有几件事等他在对话里确认。
- 你核对了什么，没核对什么：读过哪些代码，跑过哪些验证，哪些范围没有覆盖。校验通过只说明结构正确，不说明内容完整，不要把它当作完成的证明。
