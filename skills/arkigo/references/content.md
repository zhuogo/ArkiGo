# 内容怎么写

程序只检查结构。一份设计能不能让人看懂项目、让写代码的 AI 照着做对，取决于你写进去的内容。建立设计、大幅修改内容时读本文；只改一两个字段时不必。

## 这份设计要经得起两种读法

- **人从头看**：一个没参与过讨论的人打开页面，能说出这个项目为谁解决什么问题、由哪几部分组成、一件事从头到尾怎么走、哪些还没定。
- **AI 只取一块**：写代码的 AI 用 `context` 取走一个流程或模块，只凭这份材料就能实现，不需要再猜。它拿到的是这个对象、约束它的规则、验证它的验收、它读写的数据和接口、卡住它的问题。没有写成对象、没有用关系连上的内容，它拿不到。

下面的要求都从这两点来。

## 先确定要讲清什么

动手写对象之前，先从用户的话和现有材料里列出：这个项目给谁用、解决什么；有哪几块职责；哪几条主流程，以及会改变结果的支线；哪些规则在约束行为；哪些事还没定。

- 保留材料原有的术语、分组和区分。不要先套「前端、后端、数据」之类的固定分层，也不要为了整齐而凑数。
- 入口、状态变化、共用的能力、输出，追到能解释行为为止。「即时还是后台」「自动还是手动」「原始数据还是派生数据」「读还是写」这类会改变理解的区别，要写在它发生的地方。
- 分块读材料可以，只读摘要不行。没读过的范围不要写成已经了解，交付时说明哪些没覆盖。

## 什么内容写成哪种对象

| 材料里的内容 | 写成 |
| --- | --- |
| 项目为谁、要达到什么、做什么不做什么、怎样算成功 | `system` 的 `audience`、`goals`、`scopeIn`、`scopeOut`、`success`、`assumptions` |
| 谁在用、谁参与（包括外部系统） | `actor` |
| 一块相对独立的职责 | `module`，可以嵌套 |
| 一件事从触发到结束按什么步骤走 | `flow` |
| 「必须」「不能」「只有……才」「超过……就」 | `rule` |
| 被保存、被传递、有状态的东西 | `entity` |
| 对外或模块之间的调用约定 | `interface` |
| 用户看到和操作的页面 | `screen` |
| 怎样算做对了 | `acceptance` |
| 还没定的事，或已经定了但值得留下理由的选择 | `decision` |

几条分界线：

- **规则要单独成为对象，不要埋在步骤的文字里。** 步骤里写「按 `[[order.refund.needs-audit]]` 判断」，具体条件写在规则里，再用 `governed_by` 把流程或那一步连到规则。这样规则能被单独查看、单独验收、单独拍板，写代码的 AI 取材料时也一定会拿到它。一条规则只写一个约束。
- **模块是职责，不是目录。** 按「它负责什么」划分，不按代码文件夹划分。一个模块说不出职责、也没有下级时，它多半不该存在。
- **流程是「一件事」。** 有明确的触发和结束。两件能分别发生的事写成两个流程；一个流程超过十来步时，看看能不能把其中一段拆成独立的流程再用 `calls` 连起来。
- **验收写可观察的结果。** 「给定什么、做什么、看到什么」，能照着去验证。每条规则至少有一条验收用 `verifies` 指向它，否则没人知道这条规则有没有被做到。
- **不知道的事写成待定项，不要写成事实。** 见 `SKILL.md` 的「没定的事交给用户」。

## 放在哪里：归属、分组、顺序

- `parent` 决定一个对象在哪一层被看到。流程、规则、数据、接口、界面、验收、待定项都放在它所属的模块下面；跨模块的放在共同的上级，或它的主要负责方下面，再用关系连到其他模块。
- 顶层（`system` 的直接下级）是人打开页面看到的第一张图，只放角色和主要模块，一般不超过十来张卡片。细节放进模块里面。
- 同一层超过八九张卡片时用 `group` 分区，分区名用业务上的叫法。需要特定阅读顺序时写 `order`。
- 地图上，模块、流程、数据、接口、界面、角色是卡片；规则、验收、待定项不占卡片，列在一侧，并在它们约束、验证、卡住的卡片上显示数量。所以规则、验收、待定项一定要用关系连到它们作用的对象上，否则人在地图上看不出它们和谁有关。

## 写到多细

每个对象有三层文字，各有各的用处：

| 层 | 读者在哪里看到 | 写什么 |
| --- | --- | --- |
| `title` | 卡片、清单、目录 | 指明对象或动作，例如「申请退款」「大额退款需要人工审核」。不要用「核心能力」「数据处理」 |
| `summary` | 卡片、清单、搜索结果 | 一两句话说清它实际做什么、改变什么，90 个字符以内。不要写「负责处理相关逻辑」「统一管理数据」 |
| `body` 和 `notes` | 详情、文档、开工材料 | 能照着实现的完整内容 |

摘要和正文承担不同的阅读任务，可以说到同一件事。正文不能只是把摘要换个说法，也不能只写「详见源码」。

详细程度按复杂程度决定：简单的环节几句话讲完；调度、状态维护、权限、计费这类机制要展开到读者能解释它怎样运作。不要为了填满字段给每个对象硬塞内容，用不上的字段就省略。

各类型写到什么程度算够：

- **模块**：`responsibilities` 逐条写它负责的事；`boundaries` 写它不负责、容易被误以为归它的事，以及和相邻模块怎么分工。
- **流程**：`trigger` 写谁在什么情况下发起；每一步的 `action` 写成「谁做什么」，一步只做一件改变状态或做出判断的事；分支的 `when` 写明条件；会失败的步骤（调用外部服务、写入、等待人工）写 `failure`：失败后数据留在什么状态、谁会知道、能不能重试。设计里最常被漏掉的就是失败和分支。
- **规则**：`constraint` 写成能判断对错的一句话，带上具体的数值和条件；`when` 写它在什么时候起作用；`exceptions` 写例外；`rationale` 写为什么有这条规则，没有依据时不要编。
- **数据**：`fields` 写对理解行为有用的字段，不必照抄整张表；有状态的数据写 `states` 和 `stateTransitions`，这是读者最需要的部分；`ownership` 写谁负责写入。
- **接口**：`signature` 写到能调用；`errors` 写调用方需要分别处理的错误；`auth` 写谁能调。
- **界面**：`purpose` 写用户来这里要完成什么；`states` 写空、加载中、出错、无权限等状态各显示什么；有截图或稿子时放进 `assets/` 并写在 `media` 里。
- **待定项**：`question` 写成用户能直接回答的问题；每个选项的 `detail` 写选它会带来什么，让用户不用再问你就能选。

### 一个对比

不足的写法：一个模块，标题「任务管理」，摘要「统一处理后台任务」，职责「调度、执行、存储」。读者仍然不知道谁发起、为什么排队、什么时候写入、失败了怎么办；写代码的 AI 拿到它等于什么都没拿到。

讲清楚的写法，是把这个名词拆成几个各自说得清的对象：

- 模块「后台写入任务」，摘要「把后台写入请求排队，同一时刻只执行一项，避免多个任务同时覆盖状态」。
- 流程「执行一项写入任务」：接收并入队、空闲时取出、执行、写入结果并释放。「执行」这一步写明失败后怎么办。
- 规则「同一时刻只执行一项写入任务」，理由是防止状态被覆盖。
- 待定项「写入失败后是否保留输入并重试」，如果材料里没有说。用 `blocks` 指向那个流程。

这是说明颗粒度的假想例子。真实项目里的触发方式、排队范围和失败行为必须来自你实际读到的依据。

## 关系要有含义

- 按含义选关系类型，选不出来再用 `relates`，并在 `label` 里写清是什么关系。
- 关系连到最具体的对象上：是某个流程写入订单，就从那个流程连，而不是从它所在的模块连；规则只约束某一步时，连到 `流程id#步骤id`。上层的地图会自动把下级之间的关系合并显示到模块上，不需要你在模块之间再连一遍。
- 画成连线的关系（`depends_on`、`calls`、`reads`、`writes`、`uses`、`relates`）只写真实存在、对理解有用的。不要为了让图显得完整把所有卡片连起来。

## 核对原有资料没有漏掉

有旧文档、旧图或用户给的清单时，写之前先把其中的核心内容列成清单：按实际的机制、规则和区分列项，不按段落机械拆分。写完后逐项回查：

| 原资料里的一项（带出处） | 落在设计的哪里 | 结果 |
| --- | --- | --- |
| 「超过 200 元的退款要客服审核」（需求文档 3.2） | `order.refund.needs-audit` | 保留 |
| 「退款后回补库存」（需求文档 3.4） | 没有写 | 未覆盖，原因：库存模块还没读 |

- 「设计里出现了同一个词」不算覆盖。落点要真的解释了那一项的条件、顺序或区别。用 `query --search` 找落点，再用 `query --id` 读一遍确认。
- 几项合并成一个对象可以，但每一项的含义都要还在。
- 来自文档的对象在 `sources` 里写出处（文件路径，`symbol` 写章节名），以后能回去核对。
- 这份清单是你的工作稿，不写进设计。核对结果告诉用户：多少项保留、哪些合并了、哪些没覆盖以及原因。用户要求覆盖的内容还缺着时，不要说整份设计已经完成。
- 原资料里明确不做的事写进 `system` 的 `scopeOut`；原资料自相矛盾或没说清的地方写成待定项。

从一个新想法开始、没有旧资料时，不需要这张表，核对的是用户说过的每一点要求有没有落进设计。

## 交付前自己读一遍

写完后运行 `arkigo check` 看提醒，然后用 `arkigo export md` 或 `query --id` 把写进去的内容按新读者的眼光读一遍，只凭设计里的文字回答：

1. 这个项目为谁解决什么问题？每个顶层模块负责什么、不负责什么？
2. 选一条主流程，能不能从触发走到结果，说出每一步谁做什么、在哪里分支、失败了怎样？
3. 选一条规则，能不能说出它在哪个流程的哪一步起作用、怎样验证它被做到了？
4. 选一个数据，能不能说出谁写入、谁读取、有哪些状态、怎样流转？
5. 对准备开工的那部分运行 `arkigo context <id>`：只凭这份材料，能不能写出代码而不用再猜？

答不上来的地方就是要补的地方：补内容，或者写成待定项。

不要用对象数量、字数、层数来衡量设计好不好，也不要把 `check` 没有提醒当作内容完整的证明：它只看得见结构上的缺口。
