# 内容组织与覆盖审阅

首次建图、重画旧图或实质修改内容时阅读。本指引约束 AI 如何分析和解释，当前生成器不会自动检查业务覆盖，也没有内容 lint。简单查询、只改布局时不必重新审阅整张图。

## 先确定要讲清什么

先看用户问题和现有材料，列出本轮需要解释的用途、职责组、关键机制、主流程及影响结果的支线，再组织画布。读资料时保留原有术语、分组、前后条件和关键区分，不先套三列架构、固定节点数或一条简化流程。

对本轮相关的入口、状态变化、共享能力和输出追到能解释行为为止；按需继续读相关材料。控制上下文意味着分块读取，不意味着只读摘要或只留摘要。不默认扫描整仓，也不把尚未读取的范围写成已覆盖。

如果原资料明确列出多组职责或多个环节，逐项核对其含义和相互关系。归在一个模块可以，但不能只保留模块名而丢掉其内部职责。即时与后台、自动与按需、原文与派生内容、读取与写入、设计与实现等会改变读者理解的区别，应在对应位置明确解释。

## 用三层表达承载细节

| 放在哪里 | 读者应该获得什么 | 如何判断需要展开 |
| --- | --- | --- |
| 概览 | 系统用途、主要参与者、职责边界、核心协作与读图入口 | 用具体模块和有含义的连线建立全局，不把所有步骤平铺在首页 |
| 节点详情 | 该机制为什么存在、怎样工作、关键规则与异常、输入输出及依据 | 摘要已经能定位主题，但还不足以解释行为时补充详情 |
| 子视图 | 内部职责如何配合，数据和控制如何流动，分支从哪里发生 | 有多个有意义的职责、处理阶段或边界，需要分别查看、连线或继续深入时展开 |

同一机制可以有概览摘要和详细解释，两者承担不同阅读任务。避免复制整段文字，但不要因“去重”删掉概览中的必要上下文。详情也不能只是把摘要换个说法，或只写“详见源码”。

将原资料拆成职责、流程和规则后，保留来源定位以便核对，不再把已经解释的同一段全文附成另一套原文卡片。需要逐字核对、解释冲突或保留特殊措辞时才引用必要原话；去重前核对原段里的条件与边界已经进入相应解释，不能直接删掉尚未被解释的事实。

详细程度按问题决定：简单环节可以讲短；调度、上下文装配、状态维护等复杂机制要展开到读者能解释其运作。不要为填满模板给每个节点硬塞所有字段，也不要把用户要求“详细”理解为给整个项目无限展开。

## 将名词改成可解释的行为

标题应指明对象或动作，例如“装配任务上下文”，而不是“核心能力”；重要术语保留在标题或摘要，方便定位。摘要说清该节点实际改变了什么，不用“负责处理相关逻辑”“统一管理数据”代替解释。

卡片摘要承担导航，不塞入整套规则；完整条件、步骤和限制放在详情或子视图中。浏览器里摘要被截断时，改写为能完整显示的关键行为，并核对原有解释仍在详情，不通过删掉机制来缩短文字。

对核心机制，按适用性在 `details` 中说明：

- **职责与边界**：负责什么，和相邻模块如何分工；共享能力由谁负责。
- **触发与输入**：谁在什么情况下调用，使用哪些请求、配置、历史或状态。
- **处理与输出**：关键步骤与先后依赖，输出交给谁；主流程用有顺序的步骤描述。
- **数据与生效**：读取什么，写到哪里，谁拥有原始数据和派生数据；修改何时被使用。
- **规则与异常**：哪些条件改变结果，失败、冲突、取消或重试怎样处理；未知之处原样标出。
- **具体例子**：难以理解的抽象机制，用材料已有的输入、状态变化和结果走一遍；自拟例子标为演示假设。

这些是分析问题，不是必须照抄的六张卡。关键路径如果靠连线更清楚，就画出有方向、有含义的关系；如果主要是一个节点的内部规则，就在详情解释。重要的文件读写、权限或生效链决定系统行为时，应作为流程展开，不能因为属于“实现细节”而省略。

下面是假设的串行后台任务设计示例，仅说明表达颗粒度，不能据此推断真实项目存在队列或重试机制：

**不足的表达**：标题“任务管理”，摘要“统一处理后台任务”，详情只有“调度、执行、存储”。读者仍不知道谁发起、为何串行、何时写入或怎样失败。

**更明确的表达**：标题“串行执行后台写入任务”，摘要“将后台写入请求排队，同一时刻只执行一项，避免多个任务同时覆盖状态”。详情进一步写明：

```json
{
  "触发与输入": "调用方提交任务类型和待处理记录；当前设计暂定由定时器与手动操作触发。",
  "主流程": [
    "接收任务，保留任务类型和输入记录，加入等待队列。",
    "执行器空闲时取出下一项；运行中到达的新任务继续等待。",
    "成功后写入结果并释放执行位置，再处理下一项。"
  ],
  "规则": "串行约束只覆盖此执行器接管的任务；其他写入入口是否共用该约束仍待确认。",
  "异常与待确认": "失败时如何释放执行位置、是否保留输入重试、是否允许后续任务继续，尚未确定。"
}
```

如果任务类型各有独立职责、输入或生效方式，还要在详情逐项解释或建立子视图，不能用“若干任务”概括掉已有清单。真实项目的触发方式、串行范围和失败行为必须来自实际读取的依据。

## 旧资料的覆盖审阅

已有文档、旧图或明确职责清单时，在生成前提取其核心内容，生成后逐项回查。核心内容按实际机制和有意义的区分列项，不按段落机械拆分；大型资料可按本轮范围分批核对。

保留一份能回查的简短清单：

| 原资料中的核心内容及来源 | 新图落点：视图路径、节点 ID 或详情项 | 处理结果与理由 |
| --- | --- | --- |
| 某项机制及其关键区分 | 实际可找到的解释位置 | 保留 / 合并 / 未覆盖；合并说明哪些含义被保留，未覆盖说明原因与影响 |

清单少时放在概览节点的 `details` 中；已有审阅文档则沿用；材料较多时可在画布旁保存 `coverage.md` 并在概览详情指出位置。不要给 Schema 添加它不支持的审阅字段。新想法没有旧资料时，不制造对照表，记录本轮范围、假设和未知即可。

“提到了同名词语”不足以算覆盖。落点需要解释该项职责、条件、顺序或区别；一个完整解释可以覆盖多项相关内容，但仅写一个泛化模块名、来源路径或“另见其他模块”不能算已讲清。当前没有跨图语义链接时，详情写准确的模块路径、视图及节点标识，保留读懂当前行为所需的简短解释；不要伪造可点击引用或多父归属。

## 交付前的阅读验收

结构校验后，按首次接触项目的读者视角，从画布中的文字和详情完成检查：

1. 能说明系统为谁解决什么问题，并找到主要模块的职责边界。
2. 能从一个真实触发走到结果，说出关键参与者、输入输出、分支和状态变化；异步处理与后续生效需要接着追到可见结果。
3. 能解释本轮核心机制的关键区分，以及共享机制由谁负责、怎样被使用。涉及文件或数据时，能说出读写对象、归属与使用时机。
4. 对照覆盖清单逐项找到实际解释；不能从图中回答的项目补齐或列为未覆盖。用户已经要求覆盖的核心内容仍缺失时，不能把整张图宣称为完成。
5. 用一个具体问题试找解释入口，例如“修改这条配置后，谁在什么时候读到它？”；重要术语可定位，概览能引导进入细节。结构校验或搜索命中不代替阅读解释。

不要以节点数、字数、层数或关键词命中数量作为可理解性分数，也不要声称工具已经自动判定业务完整。将内容审阅、结构校验和实际浏览器检查分别报告；没有验证的就明确保留。
