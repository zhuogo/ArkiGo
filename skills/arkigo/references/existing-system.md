# 从已有项目开始

项目已经有代码，或者有需求文档、设计文档，要把现状整理成设计。这里的要求是如实：设计写的是项目现在真实的样子，每一项能回到它的出处。内容的写法见 [content.md](content.md)，字段见 [format.md](format.md)。

## 三种信息分开记

| 信息 | 怎么记 |
| --- | --- |
| 你在代码里读到的行为 | `origin: code`、`status: accepted`，`sources` 指向读过的文件和函数 |
| 文档里写明的内容 | `origin: doc`、`status: accepted`，`sources` 指向文档和章节 |
| 你对意图的推测、改进建议 | `origin: ai`、`status: proposed`，或写成待定项 |

- 代码和文档是既成事实，记为已接受，不需要用户逐条点头。「提议」留给真正要他决定的事。
- **代码和文档矛盾时**：设计写代码的实际行为，因为那是现状；再建一个待定项，写明文档怎么说、代码怎么做（各自的出处写在 `sources` 里），让用户定以哪个为准，用 `blocks` 指向那个对象。不要悄悄选一边。
- **代码这样做，但看不出为什么**：`rationale` 留空，不要编一个听起来合理的理由。这个「为什么」会影响后续改动时，写成待定项问用户。
- **你对某段代码的理解没有把握**：照你读到的写，并用一条 `warn` 的 `callout` 写明哪里没核实。
- **你发现的问题和改进点**：不要写进现状里。值得用户决定的写成待定项，其余的在汇报里说。

## 步骤

1. **定范围**。和用户确认这次要梳理的范围。项目大时不要试图一次读完：先建立整体骨架，再按用户关心的顺序逐个模块深入。

2. **读整体**。说明文档、依赖清单、入口文件、路由或命令清单、数据结构定义。用路径和符号搜索定位，跳过依赖目录和构建产物。

3. **建立骨架**。`arkigo init`，补全 `system`（项目是给谁用的、做什么；读不出来的问用户），建立角色和顶层模块。模块按职责划分，不要把目录树直接搬过来：一个职责可能散在几个目录里，一个目录也可能有几种职责。

4. **逐个模块深入**。选一条真实的行为，从入口追到结果：谁触发、经过哪些判断、读写什么数据、调用什么外部服务、失败时怎样。把它写成流程；路上遇到的判断条件写成规则，数据结构写成数据，对外的调用约定写成接口，页面写成界面。每个模块一次 `change`。

   ```json
   { "op": "add", "object": {
     "id": "order.refund.needs-audit", "type": "rule", "title": "大额退款需要人工审核",
     "summary": "单笔退款超过 200 元时进入人工审核。",
     "parent": "order", "status": "accepted", "origin": "code",
     "body": { "when": "买家提交退款申请", "constraint": "退款金额超过 200 元时，申请状态置为待审核，不发起渠道退款" },
     "sources": [ { "kind": "file", "ref": "src/order/refund.ts", "symbol": "needsAudit" } ]
   } }
   ```

5. **登记实现情况**。从代码里读出来的流程、规则、数据、接口、界面、模块，用 `implement` 记为 `implemented`，`evidence` 指向承载这段行为的文件。这一步让设计和代码建立对应：程序记下文件的指纹，以后代码一变就能发现。

   ```json
   { "op": "implement", "id": "order.refund.needs-audit", "status": "implemented",
     "evidence": [ { "path": "src/order/refund.ts", "symbol": "needsAudit" } ] }
   ```

   `sources` 说的是这项内容从哪里读来，`evidence` 说的是它在哪里实现。从代码整理时两者常常指向同一个文件，都要写。文档里写了、代码里只做了一部分的记 `partial` 并写明缺什么；文档里写了、你确认代码里没有的记 `planned`；还没去代码里找过的不要记。

6. **已有的测试**。能说明业务预期的测试可以整理成验收，`sources` 指向测试文件，用 `verifies` 连到它验证的规则或流程。只有你实际跑过，才写验收结果；读过测试代码不算。

7. **检查、核对、通读**。`arkigo check`；有旧文档时按 [content.md](content.md#核对原有资料没有漏掉) 逐项核对；再按 [content.md](content.md#交付前自己读一遍) 自己读一遍。

## 没读到的地方要看得出来

一份只梳理了一半的设计，如果看起来像是完整的，读的人会把没写的当成没有。所以：

- 还没深入的模块，写上你从整体阅读里得到的职责，并加一条 `callout` 说明「内部的流程和规则尚未梳理」。
- 一个对象的 `sources` 只写你实际读过、和这项内容有关的文件。写一个目录不代表里面的文件都读过。
- 汇报时说明：读了哪些模块、追了哪几条行为、哪些范围没有覆盖。

## 设计文档怎么处理

内容整理进设计之后，原来的需求文档和设计文档就成了第二份，以后不会有人维护。核对完成后问用户怎么处理它们（删除、归档或保留），不要自己删。用户决定移走或删除时，指向它们的 `sources` 会被 `verify` 报为缺失，按新位置更新，或改成 `doc` 并写明原文档的名称。

## 交给用户

告诉他：页面在 `docs/arkigo/index.html`；这次梳理了哪些范围、哪些没有；文档和代码不一致的地方有几处，在「待拍板」里等他定；你跑过哪些测试、没跑哪些；你发现但没有写进设计的问题。之后改代码时按 [loop.md](loop.md) 进行。
