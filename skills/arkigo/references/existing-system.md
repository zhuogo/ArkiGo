# 从已有系统开始

先明确项目根目录和此次要理解的范围。已有画布/模型时优先 query 定位模块；首次分析才读取说明、依赖清单与入口，再沿一条实际行为追踪关键调用、数据变化、分支和返回结果。使用路径/符号搜索定位，跳过依赖、产物与无关目录；不默认全文加载仓库。不要把目录树直接转换成架构图。

默认输出画布时，代码观察用 `sourceOrigin: code`，每个已分析模块的 `sources` 记录项目根目录相对的目录或入口文件；关键行为补充实际读过的文件与函数名，必要时记录当次行号。已有模型则使用 `provenance.origin: code` 与 `provenance.references`，适配器会保留来源。目录路径不代表该目录下所有文件都已分析。只记录实际存在且与本次结论有关的位置；尚未定位到实现时明确未知，不虚构路径。记录分析范围；需要复查代码版本时可另存所读文件的 SHA-256，不能当作持续监控或自动证据核验。无 Git 时不虚构提交。

已有模型或画布 JSON 时，用 [查询工具](query.md) 读取目标模块及其必要关系、来源，再打开涉及的代码文件。来源可能过时，影响本次结论的代码需重新读取；不要每次读整份 HTML 或重新扫描整个项目。

区分三种信息：

- 代码中读到的行为：来源指向具体执行位置，说明观察到什么。
- 文档声称的行为：保留文档来源，与代码冲突时直接指出。
- AI 对意图的推测或改进建议：画布用 `sourceOrigin: ai`、`proposed`，模型用 `origin: ai`；不能混入代码事实。

从代码提取的节点也保持 `proposed`，等待用户审阅建模是否准确。`designStatus` 表示设计决策，不表示实现证据。关键“为什么”不明确时建成问题；不要为了通过校验自行发明业务规则。

原有测试可以作为验收内容的来源，但只读测试源码不等于运行测试。把实际执行命令与结果单独记录。无法执行的依赖与遗漏范围要明确。

完成标准：生成器校验通过；用户可沿画布解释所选流程；关键行为可回到对应源码；用一个实际迭代问题核对受影响对象与代码位置。该影响分析仅覆盖实际读过的范围。
