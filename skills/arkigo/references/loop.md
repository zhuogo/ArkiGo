# 设计与代码的闭环

设计和代码对得上，这份设计才有用。闭环有四个时刻：写代码之前、写完之后、代码变了之后、用户拍板之后。每个时刻该做的事都不多，但漏掉一次，设计就开始和代码分开。

## 写代码之前

1. 找到这次要改的对象。不知道 `id` 时用 `arkigo query --search <关键词>`。
2. 取材料：`arkigo context <id>`。里面有这个对象、约束它的规则、验证它的验收、它读写的数据和接口、卡住它的未决问题。规则和验收是实现时必须满足的，不是参考。
3. 材料里有未决问题卡着这部分时，停下来问用户，或者只做不受它影响的部分。不要替用户选。
4. 要做的事设计里没有，或者和设计不一致时，先改设计，再写代码：
   - 用户明确要求的：直接 `change`，然后开工。
   - 你自己认为该改的：新增的内容标 `proposed`；要改已接受的内容时建一个待定项。告诉用户，等他认可后再实现这一部分。

先改设计再写代码，是因为反过来做时设计很少会被补上，下一个读设计的人或 AI 就会照着过时的内容做事。

## 写完代码之后

用一次 `change` 回写这次做了什么：

```json
[
  { "op": "implement", "id": "order.refund", "status": "implemented",
    "evidence": [
      { "path": "src/order/refund.ts", "symbol": "submitRefund" },
      { "path": "src/order/refund-audit.ts", "symbol": "auditRefund" }
    ] },
  { "op": "implement", "id": "order.refund.needs-audit", "status": "implemented",
    "evidence": [ { "path": "src/order/refund.ts", "symbol": "needsAudit" } ] },
  { "op": "verify", "id": "order.refund.audit-check", "status": "passed",
    "note": "npm test -- refund，12 项通过。",
    "evidence": [ { "kind": "file", "ref": "tests/refund.test.ts" } ] }
]
```

```bash
arkigo change --reason "实现退款申请与人工审核，回写实现情况和验收结果" --ops ops.json
```

- **实现情况写到每个被实现的对象上**：流程、规则、数据、接口、界面、模块各自记各自的。模块的实现情况不会从下级自动得出。
- **`implemented` 的标准**：你读过这段代码，它做到了这个对象描述的全部内容，包括分支和失败处理。只做了一部分写 `partial`，并在 `note` 里写明还缺什么。
- **`evidence` 指向真正承载这段行为的文件**，一般一到三个。程序会记下这些文件此刻的指纹，以后文件一变就会提醒复查。指向太多无关文件，提醒就会变成噪音；一个都不指，代码变了就没人知道。
- **验收只记实际跑过的**。`note` 写执行的命令和结果。没跑的不写；跑了没过的写 `failed`，不要留空。
- **实现过程中发现设计不对或不够**（漏了一个分支、接口多了一个字段）：在同一次回写里把设计改成实际做的样子，并在汇报里告诉用户。会改变业务行为的差异不属于此列，那是要用户决定的事。

## 代码变了之后

别人改了代码、你在别的任务里改了代码、或者用户问「设计还对得上吗」的时候：

```bash
arkigo verify                    # 全部实现依据
arkigo verify --since HEAD~10    # 另外标出这段提交里被改动过的依据文件
arkigo query --implementation stale
```

有依据变了或不见了时，`verify` 的退出码是 1，清单在标准错误里。这是它的正常结果。清单里的每一项只说明「这个文件和上次核对时不一样了」，设计是否过时要你读了代码才知道。对每一项，重新读那段代码，对照 `arkigo query --id <id>`，结论是下面之一：

| 你读到的情况 | 做什么 |
| --- | --- |
| 代码变了，但仍然做到设计描述的事（重构、改名、无关改动） | `{ "op": "confirm-evidence", "id": "…" }` |
| 行为变了，而且是用户要的变化 | 用 `update` 把设计改成现在的样子，再 `implement` 一次登记新的指纹 |
| 行为变了，没有人要求过（可能是改坏了，也可能是设计没跟上） | 不要自己决定以哪边为准。告诉用户差在哪里；需要他选时建一个待定项，选项是「改代码」和「改设计」 |
| 文件搬了位置 | `implement` 一次，用新的路径 |
| 实现被删掉了 | `implement` 改成 `planned`（还要做），或问用户这项设计是否作废 |

`confirm-evidence` 的意思是「我重新读过代码，它仍然成立」。没读就确认，等于把提醒关掉，设计从此失去发现偏差的能力。数量多到这一次读不完时，只处理读过的，其余的留着，并告诉用户还剩多少。

用户问「做到哪了」时，用 `arkigo query --implementation planned`（以及 `partial`、`unknown`）和 `arkigo check` 取数。页面上的图标展示生成时各对象的代码依据核对情况。

## 用户确认之后

用户在对话里确认提议、否决方案、选择选项或提出修改时，核对相关对象并用 `change` 写入。旧版离线页导出的文字和文件可按以下方式处理。

### 用户贴来旧版导出的文字

文字以「我在 ArkiGo 页面上做了下面这些决定」开头，写明设计目录、他看到的版本和逐条决定。把前三种决定写成修改项：

| 文字里的决定 | 修改项 |
| --- | --- |
| 接受「标题」（id） | `{ "op": "accept", "id": "…" }` |
| 否决「标题」（id）。理由：… | `{ "op": "retire", "id": "…" }`，有理由时再加一项把理由记在对象上，见下 |
| 「问题」（id）选第 N 项「选项」。理由：… | `{ "op": "decide", "id": "…", "chosen": N-1, "rationale": "…" }` |

```json
[
  { "op": "accept", "id": "order.refund.log" },
  { "op": "retire", "id": "order.refund.notify" },
  { "op": "update", "id": "order.refund.notify", "set": {
    "notes[+]": { "type": "callout", "tone": "info", "text": "用户否决：短信要花钱，先不做。" } } },
  { "op": "decide", "id": "order.refund.partial", "chosen": 0, "rationale": "先简单做" }
]
```

```bash
arkigo change --reason "用户在页面上拍板" --by "<用户的名字>" --base <他看到的版本> --ops ops.json
```

- **序号要减一**：文字里「第 1 项」是第一个选项，`chosen` 从 0 开始。写之前用文字里的选项标题和 `arkigo query --field <id> /body/options` 对一下。
- **否决的理由要留下**：设计里没有专门放否决理由的字段，用一条 `callout` 记在被否决的对象上。以后你或别的 AI 想再提同样的事时，能看到用户为什么说过不。
- **`--by` 写用户**：这些是他的决定，变更记录和待定项的「谁定的」都会记成他。
- **`--base` 写他看到的版本**：退出码 3 表示他看过之后设计又变了。用 `arkigo history` 找出那之后的变更，用 `arkigo history --show <rev>` 看有没有改到这几个对象。没改到的，去掉 `--base` 写入；改到了的，先告诉用户现在是什么样子，问他的决定是否不变。

### 用户给了一个旧版导出的文件

```bash
arkigo change --from-decisions decisions.json --reason "用户在页面上拍板" --by "<用户的名字>" --dry-run
```

先试运行，看输出里的 `decisions`：

```json
{ "base": "41734cf2a9e9", "stale": false, "comments": [ { "op": "comment", "id": "order.refund", "text": "审核超时改成 24 小时" } ], "skipped": [] }
```

- `stale` 为 `false`：去掉 `--dry-run` 再执行一次，接受、否决、选择就写入了。
- `stale` 为 `true`：用户看过之后设计变了。这时程序仍会按 `id` 写入，所以先按上一节的办法查这几个对象有没有被改过：都没改就正式执行；有改过的，先问用户，其余的用手写的修改项写入。
- `skipped` 是写不进去的条目和原因（比如对象已经不存在），要告诉用户。
- 命令不记录否决的理由。打开文件，把 `retire` 条目里的 `rationale` 按上一节的写法补成 `callout`。

### 批注

批注不会被自动写入：贴来的文字里是「对……的批注：……」，文件方式下在输出的 `decisions.comments` 里。它是用户对某个对象的意见，先 `query --id` 读那个对象，再分情况处理：

- **意见是明确的修改**（「审核超时改成 24 小时」）：按它改，对象保持已接受。这是用户的要求，`--by` 写用户，`--reason` 写明是按哪条批注改的。
- **意见需要你来设计，或者有不止一种改法**（「这一步太麻烦了」）：你的方案是提议。新增的对象标 `proposed`；要改已接受对象的内容时建一个待定项，选项里写清每种改法和「保持现状」，用 `blocks` 指向那个对象。
- **意见是一个问题**：直接回答用户。答案说明设计没写清楚时，把设计补清楚。

### 写入之后的跟进

决定写进去只是记录了结论，结论带来的修改还要你来做：

- **待定项有了结论**：读它选中的选项，把被它卡住的对象改成结论要求的样子。这是用户已经决定的事，直接改，`--reason` 写明依据的是哪个决定。结论是「保持现状」时不用改。
- **对象被否决**：看别处是否还依赖它。步骤文字里引用着它、有验收指向它时，把这些地方一并改掉或作废。
- **写过代码的对象被改了**：设计和代码又不一致了。告诉用户哪些代码需要跟着改；他让你改时回到「写代码之前」。

最后告诉用户：写入了哪些，哪些没写入以及原因，每条批注是怎么处理的，有没有新的提议等他看。
