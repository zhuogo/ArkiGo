# 从想法开始

用户有一个想法、几句需求或一份需求文档，还没有代码。你要把它整理成一份用户能看懂、能拍板、之后能照着实现的设计。内容的写法见 [content.md](content.md)，字段见 [format.md](format.md)。

## 先分清哪些是用户说的

一个想法变成设计，大部分细节是你补的。这份设计最重要的一点，是让用户一眼分得清哪些是他说的、哪些是你提的：

- 标成 `origin: user`、`status: accepted` 的对象，里面的每一句都应该能在用户的话或他给的文档里找到。可以在 `sources` 里记下出处（`conversation` 或 `file`）。
- 你补充了会影响做法的内容（步骤怎么走、数值是多少、失败了怎么办）时，这个对象标 `origin: ai`、`status: proposed`。用户只说了「要能退款」，你写出了五步的退款流程，这个流程是你的提议。
- 两种做法都说得通、而选哪种会改变产品时，不要选一种写成提议，写成待定项让用户选。

这样第一版里会有不少提议，这是如实的：用户只说了几句话，其余的确实需要他过目。他可以在对话里逐条确认或同意整批，你再用 `accept` 写入，`--by` 写他的名字。

## 什么时候追问

只有缺的信息会改变整体方案时才先问：给谁用、要解决的核心问题是什么、有没有不能碰的限制。其余的不要用一长串问题挡住用户，先按合理的理解写出第一版，把没定的地方写成待定项。用户看着一份具体的设计做选择，比凭空回答问题容易得多。

用户没有提到的功能不要替他加。你认为少了什么时，写成一个待定项问他要不要；他明确说以后再做的，写进 `system` 的 `scopeOut`。

## 步骤

1. **建立**：在项目根执行 `arkigo init --id <英文短名> --title "<项目名>"`。

2. **项目本身和角色**（第一次 `change`）：补全 `system`，建立 `actor`。

   ```json
   [
     { "op": "update", "id": "shop", "set": {
       "summary": "给独立卖家用的小店：上架商品、收款、发货、处理退款。",
       "body.audience": ["没有技术团队的独立卖家", "他们的买家"],
       "body.goals": ["卖家一天内能开店并收到第一笔款"],
       "body.scopeIn": ["商品、订单、支付、退款"],
       "body.scopeOut": ["多店铺", "分销"],
       "body.success": ["首批 20 个卖家里有 15 个完成首单"]
     } },
     { "op": "add", "object": { "id": "buyer", "type": "actor", "title": "买家", "summary": "在小店里下单和申请退款的人。",
       "parent": "shop", "status": "accepted", "origin": "user", "body": { "goals": ["买到商品", "出问题时能退款"] } } }
   ]
   ```

   目标、范围、成功标准里用户没说过的，不要写进 `system`（它是已接受的）。需要他定的写成待定项；你为了继续往下写而做的假设写进 `assumptions`，并在汇报时说明。

3. **顶层模块**（一次 `change`）：按职责划分，每个模块写清负责什么、不负责什么。这是用户打开页面看到的第一张图。

4. **逐个模块展开**（每个模块一次 `change`）：它的流程、规则、数据、接口、界面、验收、待定项，连同它们之间的关系。先写用户最关心的主流程，写到分支和失败都有交代。同一组修改里先 `add` 对象，再 `link`。

5. **跨模块的关系**：模块都建好之后，补上跨模块的调用、读写和依赖。

6. **检查和通读**：`arkigo check` 看提醒，然后按 [content.md](content.md#交付前自己读一遍) 自己读一遍，核对用户说过的每一点要求都落进了设计。

分批写入是为了让每一批都能通过校验、出错时容易定位，也让命令历史里的每条记录说得清是什么。不要把整份设计塞进一次 `change`。

## 写到哪里为止

- 用户这次要做的范围写到能照着实现；他明确说以后再做的只在 `scopeOut` 里列出。不要因为用户说「详细一点」就把产品范围扩大。
- 还没有代码时不需要写实现情况。用户确认了要开工的范围之后，可以把这部分对象用 `implement` 标成 `planned`。
- 验收写的是预期的结果，不表示已经验证过，不要写验收结果。

## 交给用户

告诉他：页面在 `docs/arkigo/index.html`；设计里哪些是他说的、哪些是你的提议；有几个问题要在对话里确认；你做了哪些假设；他说过的要求里有没有还没写进去的。路线图怎么看，见 [page.md](page.md)。

用户拍板之后的处理见 [loop.md](loop.md#用户确认之后)；设计定下来开始写代码时，按 [loop.md](loop.md) 进行。
