# 从想法开始

提取角色、目标、本轮范围和限制。只有缺失信息会改变核心方案时才追问；其余保留为标明来源的建议或问题。用户尚未选择具体案例时，可以明确说明使用演示需求，不能把演示规则写成用户要求。

组织一个系统、必要模块、一条从触发到结果的核心流程。补充会影响结果的分支、失败处理、业务规则及可核对的验收。暂不展开未来功能。

默认写 `arkigo-canvas/1` 输入，按画布指引组织系统概览、模块子视图和必要连线。用户原话或输入文件写入 `sources`；AI 新增方案标为 `sourceOrigin: ai`、`designStatus: proposed`。范围、假设和未深入模块在文档 description 或相关节点 details 中说明；待定事项单独建节点或在相关详情中明确标识，不用肯定语气补齐未知需求。

只有用户已有或明确需要 `0.1-draft` 设计模型时，才读模型约定，使用 `provenance`、`project.assumptions` 和 `question` 等模型字段。不要为同一份内容无条件维护模型与自定义画布两份数据。

尚未实现的模块不要求有代码路径。若本轮需要讨论代码组织，可在 `details` 中记录“计划位置”；来源仍指向需求或建议。实现后实际读取代码，再补充对应目录、文件和函数，不将规划位置当作已有实现。

完成标准：生成器校验通过并产出可打开的画布；模块职责和主流程可读；用户能找到尚未决定的事项。验收描述表达预期，不表示测试已执行。
